## Шаги (Steps)

Флажь `high`, если:
- поле `action` у шага пустое или состоит только из пробелов, И при этом `expected` этого шага НЕ описывает просто наступившее состояние системы (форма отобразилась, страница загрузилась, поле заполнено). Шаг без действия невыполним.
- Если `action` пустой, но `expected` описывает именно наступившее состояние без действия пользователя — это не «пустой action», а шаг-дубль ожидаемого результата. Флажь `low` по правилу ниже, не `high`.
- шаг использует объект или состояние, которое создаётся только в более позднем шаге. Пример: шаг 2 удаляет запись, которую создаёт шаг 5.
- порядок шагов логически невозможен.
- expected result не соответствует действию в action.

Флажь `medium`, если:
- один шаг содержит несколько независимых действий через запятую. Пример: `ввести email, ввести пароль, нажать кнопку`. Это три разных шага.
- шаг описывает расплывчатую цель без конкретного критерия. Примеры: `убедиться, что система работает`, `проверить корректность`. Непонятно, что именно проверять.
- пропущен важный переход или действие. Без него следующий шаг невозможен.

Флажь `low`, если:
- есть лишние технические шаги, не относящиеся к тесту. Примеры: `открыть браузер`, `ввести адрес сайта` (без конкретного URL — просто инструкция открыть браузер и набрать адрес).
- шаг описывает наступившее состояние системы, а не действие пользователя. Пример: `Отображается форма ввода кода`, `Страница обновилась` — это expected result предыдущего шага, а не самостоятельный шаг. Такой шаг дублирует ожидаемый результат.
- первый шаг — навигация к URL, а в preconditions уже описано состояние «Открыта страница X» или «Пользователь находится на странице X». Навигационный шаг дублирует предусловие.
- шаги 1–N — это login-флоу (ввод логина, ввод пароля, нажатие кнопки входа), а в preconditions уже описано состояние «Пользователь авторизован» или «Введены корректные учётные данные / Пользователь успешно авторизован». Login-шаги дублируют предусловие. Флажь только если precondition явно описывает состояние ПОСЛЕ логина — не флажь если precondition описывает только «Открыта страница входа».
- action содержит технические термины автоматизации: `по локатору`, `selector`, `xpath`, `css selector`, `id элемента`. В ручном тест-кейсе такие термины недопустимы.

Не флажь, если:
- действия физически нераздельны. Пример: `нажать и удерживать`. Это одна атомарная операция.
- шаг содержит конкретный observable критерий. Примеры: `Убедиться, что URL содержит /auth/login`, `Проверить статус ответа 200`. Это конкретная проверка, а не расплывчатая цель.
- требуемое состояние не описано в preconditions. Это нарушение правила `preconditions`, не `steps`.
- шаг "открыть страницу" или "перейти по адресу" содержит конкретный URL в тексте action. Это нарушение правила `test_data` (URL должен быть в поле test_data, а не в тексте action), не лишний шаг. Не флажь как low по steps.
- URL или данные вписаны в action. Это нарушение правила `test_data`, не `steps`. Не создавай issue по `steps` если нарушение уже описано в правиле `test_data`. Одна причина — один issue. Неправильно: issue по правилу `steps` с текстом вида «Шаг N содержит URL, что нарушает правило test_data» — раз нарушение уже про `test_data`, по `steps` его создавать нельзя вообще, даже с упоминанием test_data в тексте.
- шаг ожидания результата асинхронной операции (email, SMS, очередь, cron) отсутствует. Не флажь как лишний шаг — ожидание асинхронного результата является частью сценария.

Если флажишь «несколько действий в одном шаге»: в recommendation напиши: `Разбить шаг N на X шагов: [шаг 1], [шаг 2]...`. Данные из action перенести в test_data.

Если флажишь «расплывчатая цель»: в recommendation предложи конкретное переформулирование с observable критерием: элемент, текст, статус, URL. Не предлагай другую форму «убедиться, что...».

## Как исправлять

Если issue о нескольких действиях в одном шаге: раздели на отдельные шаги. Данные из action → test_data. Для каждого нового промежуточного шага добавь очевидный expected result из контекста действия:
- «ввести email» → «Поле email заполнено без ошибок»
- «ввести пароль» → «Поле пароль заполнено без ошибок»
- «нажать кнопку» → берётся из оригинального expected result исходного шага

Если issue о расплывчатой цели: переформулируй в конкретное действие с observable критерием (элемент, текст, URL, статус). Не предлагай форму «убедиться, что...». Если критерий неопределим из контекста → `manual_needed`: «Укажи observable критерий для шага N.»

Если issue о пустом `action`: сначала проверь, не описывает ли `expected` этого шага наступившее состояние системы без действия пользователя (форма отобразилась, страница загрузилась и т.п.). Если да — это шаг-дубль ожидаемого результата: удали шаг, как описано ниже, не выдумывай для него action. Если `expected` требует реального действия пользователя, но какое именно — не следует из контекста → `manual_needed`: «Укажи действие для шага N.» Не сочиняй action, переформулируя expected другими словами — это не действие, а тот же факт.

Если issue о нарушении порядка шагов или пропущенном переходе → `manual_needed`.

Если issue о технических терминах автоматизации: удали технический термин, сохрани человекочитаемое описание действия. Пример: `Нажать кнопку по локатору «X»` → `Нажать кнопку «X»`. Если название элемента неизвестно из контекста → `manual_needed`.

Если issue о шаге-дубле ожидаемого результата: удали шаг. Его содержимое уже есть в expected result предыдущего шага.

Если issue о навигационном шаге, дублирующем precondition: удали навигационный шаг. Предусловие уже описывает нужное состояние.
